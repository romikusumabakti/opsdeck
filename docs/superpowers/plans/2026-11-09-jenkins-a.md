# Retire Jenkins part A (container apps + deleting environments) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let engineers delete an environment cleanly from the Panel, with an off-server backup first; let admins adopt existing Cloudflare hostnames into the Panel; then move the remaining container-app Jenkins jobs to Woodpecker + Panel.

**Architecture:**
- **Teardown mirrors provisioning:** an ordered, idempotent, resumable list of steps per environment (`teardown_steps`), run by a BullMQ job that logs to a run.
- **Archives:** the first steps dump the database and tar the deploy dir to the instance backup destination (S3 connection or local), recorded in `environment_archives` and pruned after 30 days.
- **Adoption:** an admin action records an existing hostname's DNS record, Access app and tunnel route as the environment's domain, so the Panel can remove them later.
- **Rollout:** Tasks 1–8 are opsdeck code. The Rollout section is a controller runbook with Romi: DSS repos, Woodpecker, Cloudflare and Jenkins.

**Tech Stack:** Bun, Hono, Drizzle (migrator rules), BullMQ/Valkey, ssh2 via `lib/ssh.ts`, the Cloudflare API via `lib/cloudflare/api.ts`, `@aws-sdk/client-s3` via `lib/instance-backup/destination.ts`, React 19 + TanStack + shadcn/ui (Base UI), Vitest.

**Spec:** `docs/superpowers/specs/2026-11-09-jenkins-a-container-apps-design.md`. Recon (scratch, not committed): `docs/superpowers/specs/recon-2026-11-09-project-4a.md`.

## Global Constraints

- **Migrations:** Drizzle, expand-only. No BEGIN/COMMIT. The first statement is `SET LOCAL lock_timeout = '5s';`. New migration dir: `drizzle/20261113000000_environment_teardown/`.
- **Errors:** RFC 9457 problem+json with a stable `code`, and messages in all 5 locales (`messages/*` like existing `actionErrors`). The API sends no display prose.
- **Who may delete:**
  - Project `environment:delete`: engineers on their own project, and org admins.
  - **Production** (`environments.kind = 'prod'`): engineers are refused with `environmentIsProduction`. Admins must also send `confirmProduction: true`.
  - **Escrowed variables:** the existing escrow guard of `deleteEnvironment` (`integration:manage` + `confirmEscrowedDeletion`) applies to both full delete and remove-from-Panel.
- **"Remove from Panel only"** is today's row-only delete, kept for org admins only: `canOrg(role, { server: ["manage"] })`.
- **Archives:**
  - **Location:** the instance backup destination: `loadBackupDestination()` (S3 key prefix `opsdeck-env-archives/<instance>/<archiveId>/`), else local `${LOCAL_BACKUP_ROOT}/<instance>/env-archives/<archiveId>/`.
  - **Retention:** kept **30 days** (`ENV_ARCHIVE_RETENTION_DAYS = 30`).
- **Destructive commands:**
  - `rm -rf` only on a path that is absolute, has no `..`, is not `/` or a top-level dir, and equals the target's `deployDir`.
  - `compose down` only in a target's `deployDir`.
  - Secrets never reach argv or logs (use `redactSecrets`, as provisioning does).
- **Simple by default:** one confirm (type the environment name). "Remove from Panel only" sits under the existing "Advanced options" Collapsible.
- **Tests:** `env -u SECRETS_KEY bun --bun vitest run --maxWorkers=3` (never more workers; the laptop runs out of memory). Lint: `bunx biome check .` (not `bun run check`, which writes). Types: `bun run typecheck`.

## Review Focus

1. **The archive fails or is partial** (S3 down, pg_dump error, disk full): nothing destructive may run. The job stops at the archive step, which shows a code, and retry resumes there. *Test in Task 5.*
2. **A retry after a crash between steps:** every step is idempotent. Retrying `stack_down` on a dir already gone succeeds, and so does `remove_dns_record` on a record already deleted. A finished archive is not re-taken, and no second archive row is created. *Tests in Tasks 3–5.*
3. **A deploy dir shared with another environment, discovered late** (the other environment was created after the plan was built): `remove_deploy_dir` and `stack_down` re-check at run time and refuse with `deployDirShared`. *Test in Task 4.*
4. **Hostile or odd `deployDir` values** (`/`, `/deployments`, `/deployments/../etc`, trailing slash, spaces): refused before any SSH. *Test in Task 4.*
5. **Concurrency:** a deploy or provisioning run active on the environment refuses the teardown with `environmentBusy`; a second teardown request refuses with `teardownRunning`. *Test in Task 5.*

### Task 3: Teardown plan and refusals

**Files:**
- Create: `lib/teardown/plan.ts`, `lib/teardown/errors.ts`, `lib/teardown/repository.ts`
- Test: `tests/teardown-plan.test.ts`

**Interfaces:**
- Consumes: the schema from Task 1 and the existing tables `deploy_targets`, `environment_services`, `environment_domains`, `environments`.
- Produces:
  - `TeardownStepSpec`, a discriminated union by `kind` with a zod schema `teardownStepSpecSchema` (re-validated at run time, like `provisioningStepSpecSchema`). Params:
    - `check_stack {serverId, deployDir}`;
    - `archive_database {serviceId}`;
    - `archive_deploy_dir {serverId, deployDir}`;
    - `stack_down {serverId, deployDir}`;

    - `delete_environment {}`.
  - `buildTeardownPlan(environmentId): Promise<{ steps: TeardownStepSpec[] } | { refusal: TeardownRefusal }>`. Order:
    1. one `check_stack` per distinct (server, dir);
    2. `archive_database` per db service;
    3. `archive_deploy_dir` per distinct (server, dir);
    4. `stack_down` per distinct (server, dir);

    6. the domain removals (only for ids that are set);

    - `environmentBusy`;

  - `saveTeardownSteps(environmentId, steps)` and `listTeardownSteps(environmentId)` in the repository.

### Task 5: Archive steps and the teardown runner

**Files:**
- Create: `lib/teardown/archive.ts`, `lib/jobs/teardown.ts`

**Interfaces:**
- Consumes: `loadBackupDestination()`, `ObjectStore`, `LOCAL_BACKUP_ROOT`, `instanceName()`; Tasks 2–4.
- Produces:
  - `archiveDatabase(ctx, {serviceId})`:
    - docker: `docker exec <container> pg_dump -Fc -U postgres <db>` streamed over SSH to a temp file;
    - shared: the same against the database host;
    - then upload as `db-<db>.dump`.
  - `archiveDeployDir(ctx, {serverId, deployDir})`: `tar -C <parent> -czf - <base>` streamed, uploaded as `deploy-<slug>.tar.gz`.
  - Both: get-or-create the environment's `environment_archives` row (one per teardown, its id stored in the first archive step's params on first success) and append `{name, size}`. A file already listed is not re-uploaded.
  - `runTeardown(data): Promise<{ status: "success" | "failed" }>`: same structure as `runProvisioning` (skip `done`, mark `running`/`done`/`failed`, log to the run, `redactSecrets`, close the run on escape).
    - Before `delete_environment`, it sets `environment_archives.completed_at`.
    - `delete_environment` deletes the environment row, and the cascade removes steps and runs. Activity `environment.deleted` records `{environment, archiveId}`.
- The archive happens before any destructive step by plan order, so a failed archive leaves everything in place.
