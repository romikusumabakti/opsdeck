# Retire Jenkins, part C: releases and Jenkins off — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Engineers mark a tested legacy build as a client release in the Panel and download that exact artifact, so the Jenkins `RELEASE-*` / `UAT-*` jobs and then Jenkins itself can go.

**Architecture:**
- A `releases` table records each release against its source deployment.
- A worker job copies the artifact from the registry (part B's `openArtifactLayer`), packages it (jar as is, `dist` as zip) and stores it in the Panel's Garage via the existing `ObjectStore`.
- The API streams downloads behind a new project permission `release`.
- Jenkins is switched off afterwards in an operations task.

**Tech Stack:** Bun, Hono, React 19 + TanStack, shadcn/ui (Base UI), Drizzle/Postgres, BullMQ, `@aws-sdk/client-s3` (Garage), `yazl`, Vitest, Biome.

**Spec:** `docs/superpowers/specs/2026-11-11-jenkins-c-releases-design.md`

## Global Constraints

- **Migrations:**
  - Each is a folder `drizzle/<YYYYMMDDHHMMSS>_<name>/` holding `migration.sql` + `snapshot.json`. The timestamp must sort after `20261114000000`.
  - The first line is `SET LOCAL lock_timeout = '5s';--> statement-breakpoint`. No BEGIN/COMMIT. Changes are additive.
  - Each migration gets a static test.
- **Scope:** releases exist only for deploy targets of kind `jar` or `static`.
- **Release source:** a release comes from a deployment with status `success` of such a target in an environment of the release's project, on any branch.
- **Version and notes:**
  - The version is required: trimmed, 1–100 characters, no control characters.
  - Notes are optional: up to 2000 characters. They are the only editable field.
  - The version is unique per (project, component) among releases that are not `failed`.
- **Packaging:**
  - The artifact is the layer of `<componentKey>-deploy:<tag>` under `bundle/artifact/`.
  - A jar is stored as is: the single `*.jar` file.
  - Static output is stored as one `.zip` of the `bundle/artifact/` tree, with paths relative to it and `index.html` at the zip root.
- **Download file name:** `<componentKey>_<versionSlug>.<jar|zip>`, where `versionSlug` replaces every run of characters outside `[A-Za-z0-9._-]` with `-` and trims `-` from both ends.
- **Storage:**
  - The Panel's Garage, through `garageSource()` (lib/instance-backup/destination.ts).
  - Object key: `releases/<projectId>/<componentKey>/<releaseId>/<fileName>`.
  - Releases are kept forever; only an admin (org `server:manage`) deletes one, which also deletes its object.
- **Permissions:**
  - New project permission `release: ["create", "download"]`, granted to `engineer` only (not `qa`, not `viewer`).
  - Listing releases needs `deploy: ["view"]`.
- **Audit:** `activity_log` gets `release.created`, `release.downloaded` and `release.deleted`, with data `{ project, component, version }`.
- **Copy:** user-facing copy goes in `messages/*.json`. Every catalog gets the keys (a parity test enforces this); en and id are translated, ar/es/zh carry the English text.
- **Tests:** full suite `bun run test > /tmp/suite.log 2>&1`, and `grep -cE "FAIL|×" /tmp/suite.log` must print `0` before each commit. Also run `bunx tsc --noEmit -p .` and `bunx biome check <files>`.
- **Secrets:** registry credentials and Garage keys never appear in output, errors or logs.

## Review Focus

1. **The registry no longer has the tag** (pruned by `ci-disk-maintenance`). Expected: the release becomes `failed` with "The build's artifact is no longer in the registry", and its version can be used again. Owner: Task 3.
2. **Download while the release is still `preparing`, or after it `failed`.** Expected: 409 with a clear message, and no partial file. Owner: Task 4.
3. **A QA or viewer member** calls create or download. Expected: 403. Listing still works for them. Owner: Task 4.
4. **A 130 MB jar download.** Expected: it streams, with `Content-Length`, and is never buffered whole in memory. Owner: Task 4.
5. **Mark-as-release on a deployment that is not `success`, or whose target is `compose`.** Expected: 409 or 400, and no row. Owner: Task 3.

### Task 2: Package an artifact layer into a release file

**Files:**
- Create: `lib/releases/package.ts`
- Test: `tests/release-package.test.ts`

**Interfaces:**
- Produces:
  - `releaseFileName(componentKey: string, version: string, kind: "jar" | "static"): string`, per the Global Constraints rule;
  - `packageArtifactLayer(layer: ReadableStream<Uint8Array>, kind: "jar" | "static", outDir: string, fileName: string): Promise<{ filePath: string; sizeBytes: number; sha256: string }>`.
- Behaviour of `packageArtifactLayer`:
  - It gunzips and reads the tar entries under `bundle/artifact/`, with no shell and no `tar` binary.
  - jar: there must be exactly one regular `*.jar` entry. It is written as `outDir/fileName`.
  - static: there must be an `index.html` entry. Every regular file is added to a zip (`yazl`) at its path relative to `bundle/artifact/`.
  - It refuses any entry path containing `..` or starting with `/`.
  - On a violation it throws `ReleasePackageError` with the message `artifact must contain exactly one jar` / `static artifact has no index.html` / `unsafe path in artifact`.
  - Tar parsing: use the `tar-stream` package (add it as a dependency; it is the standard streaming tar reader, about 20 KB), not a hand-written parser.

- [ ] **Step 1:** Write the tests. Build the gzip tars in the test with `tar-stream`'s pack plus `zlib.gzip`.
  - jar → the file's sha256 equals the input's;
  - two jars → error;
  - static `dist` with `index.html` + `js/app.js` → the zip lists exactly `index.html`, `js/app.js`;
  - static without `index.html` → error;
  - an entry `bundle/artifact/../x` → error;
  - `releaseFileName("legacy-core-backend", "TMLI 2026/11 #2", "jar") === "legacy-core-backend_TMLI-2026-11-2.jar"`.
- [ ] **Step 2:** Run. Expected: FAIL.
- [ ] **Step 3:** Implement, then add the dependency: `bun add tar-stream @types/tar-stream`.
- [ ] **Step 4:** PASS; full suite 0 FAIL.

### Task 3: Release service and preparation job

**Files:**
- Create: `lib/releases/repository.ts`, `server/services/releases.ts`, `lib/jobs/release.ts`
- Modify: `lib/jobs/payloads.ts` (job `"release/prepare.requested": { releaseId, runId }`), `lib/jobs/processor.ts` (dispatch)
- Test: `tests/releases-service.test.ts`, `tests/release-job.test.ts`

**Interfaces:**
- Consumes:
  - Task 1 schema;
  - Task 2 `packageArtifactLayer`, `releaseFileName`;
  - part B `openArtifactLayer(image, tag)`, `ArtifactImageError`;
  - `garageSource()`;
  - `requireProjectPermission`;
  - `lib/activity.ts`.
- Produces (`server/services/releases.ts`):
  - `createRelease(environmentId: string, input: { deploymentId: string; version: string; notes?: string | null }): Promise<{ releaseId: string; runId: string }>`.
    - It requires `release: ["create"]` on the environment's project.
    - The deployment must belong to that environment, have status `success`, and its target kind must be `jar`/`static`; otherwise 409 `releaseSourceInvalid` (400 when the kind is compose).
    - It inserts the row as `preparing` with snapshots of branch/tag/commit/environment name, opens a run of kind `release`, enqueues the job, and logs `release.created`.
    - A unique violation returns 409 `releaseVersionTaken`.
  - `listReleases(projectId: string): Promise<{ releases: ReleaseRow[]; totalBytes: number }>`. It requires `deploy: ["view"]`; rows are newest first, including creator name and status.
  - `updateReleaseNotes(id: string, notes: string | null): Promise<Release>`. It requires `release: ["create"]`.
  - `deleteRelease(id: string): Promise<void>`. It requires org `server: ["manage"]`, deletes the Garage object if any, then the row, and logs `release.deleted`.
  - `openReleaseDownload(id: string): Promise<{ stream: Readable; fileName: string; sizeBytes: number }>`.
    - It requires `release: ["download"]`.
    - A status other than `ready` → 409 `releaseNotReady`.
    - It logs `release.downloaded`.
- Produces (`lib/jobs/release.ts`): `handlePrepareRelease(data)`. It:
  1. calls `openArtifactLayer(component.bundleImage, release.tag)`;
  2. packages into a temp dir;
  3. calls `store.upload(key, filePath)`;
  4. sets status `ready` with `object_key`, `file_name`, `size_bytes`, `sha256` and `ready_at`, and finishes the run.

  Its failure messages:
  - "not found in the registry" → `failed` with error `The build's artifact is no longer in the registry`;
  - an `ArtifactImageError` or `ReleasePackageError` → `failed` with its message;
  - Garage missing (`garageSource()` null) → `failed` with `Release storage is not configured`.

  The temp dir is always removed.

- [ ] **Step 1:** Write the tests, with mocks for the registry, Garage and queue in the style of `tests/deploy-job-artifact.test.ts`. Cover:
  - create from a success jar deployment → row `preparing` + enqueue;
  - from a failed deployment → 409;
  - from a compose target → 400;
  - a QA user → 403;
  - a duplicate version → 409, but allowed again after the first release `failed` (Review Focus 1, Review Focus 5);
  - job happy path → `ready` with size/sha and the key `releases/<projectId>/<componentKey>/<id>/<file>`;
  - job with a registry 404 → `failed` with the exact message;
  - temp dir removed on failure;
  - `deleteRelease` by a non-admin → 403; by an admin → `store.delete([key])` then the row is gone.
