# SSH Keys and Host Key Verification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Panel reaches every server with one instance ed25519 key, restricted with `from=`, and verifies a pinned host key on every connection. Stored root passwords disappear once key login is proven.

**Architecture:**
- **One connection factory.** `lib/ssh-connect.ts` builds every ssh2/node-ssh connect config: key or password, plus a `hostVerifier` against the pin. The 9 existing clients use it: six in `lib/ssh.ts`, two in `lib/explorer/sftp-pool.ts`, one in `lib/terminal/ssh-shell.ts`.
- **Key material and file editing.** `lib/ssh-keys.ts` holds the instance key and the pure helpers that build and merge `authorized_keys` lines.
- **Server actions.** `server/services/server-keys.ts` runs move, reinstall, trust, and the bulk move and rotate jobs.
- **Sudo.** A small `privileged()` helper replaces the `printf <password> | sudo -S` plumbing. Root runs commands directly, NOPASSWD users use `sudo -n`, and password servers keep today's form.

**Tech Stack:** Bun, Hono, ssh2 (`utils.generateKeyPairSync('ed25519')`, `hostVerifier`, `hostHash`), node-ssh, Drizzle migrator, BullMQ, React 19 + TanStack, shadcn/ui on Base UI.

**Spec:** `docs/superpowers/specs/2026-11-09-ssh-keys-design.md`

## Global Constraints

- **Secrets:**
  - The private key and server passwords are never sent to the browser, never logged, never in argv, and never in error messages.
  - `redactSecrets` keeps covering passwords.
  - The private key is stored encrypted with `lib/secrets.ts`.
- **Host verification is mandatory on every connection path.** A mismatch refuses before any auth, with code `hostKeyMismatch`.
- **`authorized_keys` line format (exact):** `from="<addr>",no-agent-forwarding,no-X11-forwarding ssh-ed25519 <base64> opsdeck:<instance>:<key-id>`. Here `<instance>` is `COMPOSE_PROJECT_NAME`, falling back to `opsdeck`. Other lines are never modified. The file is 0600 and `~/.ssh` is 0700.
- **Permissions:** move, reinstall, trust, move-all and rotate require org `server:manage`.
- **Error codes** are stable strings, with messages in all 5 `messages/*.json` (en and id are real translations): `hostKeyMismatch`, `keyInstallFailed`, `keyLoginFailed`, `unreachable`, `sudoNeedsPassword`, `noPassword`.
- **Migrations** follow the Drizzle migrator rules: no BEGIN/COMMIT, `SET LOCAL lock_timeout = '5s'` first, expand only. `servers.password` becomes nullable and nothing is dropped.
- **UI is simple by default.** The password field moves under "Advanced options", and only while `auth=password`.
- **Commits** are conventional, in English. Before each commit run `bun run check`, `bun run typecheck`, and `env -u SECRETS_KEY bun --bun vitest run --maxWorkers=3`. The laptop has limited memory, so use `--maxWorkers=3`.

## Review Focus

1. **Two first connections race to pin the same server.** Exactly one pin wins (`UPDATE … WHERE host_key IS NULL`), and the loser compares against the stored pin. Task 3 test `concurrent first connections pin once`.
2. **`authorized_keys` arrives in an unexpected shape:** missing, CRLF, no trailing newline, an old line with the same marker, or `~/.ssh` as a symlink. The merge keeps every other line byte for byte, replaces only our marker line, and refuses a symlinked `~/.ssh`. Task 2 tests `merge keeps foreign lines`, `replaces same marker`, `handles CRLF and no newline`; Task 5 test `refuses symlinked .ssh`.
3. **Key install succeeds but the key-only login fails.** The line just added is removed, the password is kept, and the code is `keyLoginFailed`. Task 5 test `verification failure rolls back`.
4. **An admin edits a server's host.** The pin and key state reset (`auth=password` only if a password exists, otherwise a `noPassword` hint asks for a reinstall), so a new address never inherits an old pin. Task 3 test `host change clears pin`.
5. **A non-root user without NOPASSWD sudo.** The move is refused with `sudoNeedsPassword`, and the password is kept. Task 5 test `non-root without nopasswd refused`.

### Task 3: Connection factory with host key pinning, used by every client

**Files:**

- Test: `tests/ssh-connect.test.ts`, existing `tests/ssh*.test.ts` updated

**Interfaces:**
- Produces:
  - `type SshTarget = { serverId: string | null; host: string; username: string; password: string | null }`
  - `connectConfig(target: SshTarget, opts?: { keyOnly?: boolean; passwordOnce?: string; actor?: string }): Promise<ConnectConfig>`
    - It returns the ssh2/node-ssh config: `privateKey` from the server's `ssh_key_id` when `auth=key`, else `password` (or `passwordOnce`).
    - It always includes a `hostVerifier`. The verifier accepts the pinned key. When there is no pin and `serverId` is set, it pins atomically and records activity `server.hostKeyPinned` with the actor (`system` for jobs). On a mismatch it stores `host_key_offered_fingerprint` and rejects.
    - For an unsaved target (`serverId: null`, the new-server form test) it accepts and returns the observed key through `opts`.
    - The thrown error carries code `hostKeyMismatch`.
  - `trustOfferedHostKey(serverId: string, actorId: string): Promise<void>`: re-pins on the next connection by clearing the pin and the offered value, and records activity.
  - The `lib/ssh.ts` functions take `SshTarget` instead of `{ host; username; password }`. Callers pass the server row (id, host, username, password).

**Interfaces:**
- Consumes: Tasks 2–4.
- Produces:
  - `moveServerToKey(serverId: string, actorId: string, opts?: { passwordOnce?: string }): Promise<{ ok: true } | { ok: false; code: string }>`
    1. Connect with the password (or `passwordOnce`), with host verification.
    2. If the user is not root and `sudo -n true` fails, return `sudoNeedsPassword`.
    3. Read `$SSH_CLIENT` and compute `fromAddress` (own subnet from the app container's network; see below).

    6. Verify by key only (`keyOnly: true`).
    7. On success: `auth=key`, `ssh_key_id`, `ssh_from`, password set to null, `key_error` null, activity `server.keyInstalled`. On failure: remove the line again, keep the password, set `key_error`, return the code.

    - `POST /api/servers/:id/reinstall-key` with body `{ password }`; the password is used once and never stored
    - `POST /api/servers/:id/trust-host-key`
